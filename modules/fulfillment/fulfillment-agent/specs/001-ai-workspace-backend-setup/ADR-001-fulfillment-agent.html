01Context

The Fulfillment team is building the Fulfillment Agent, which starts with Delivery Options and predefined logistics diagnostics but must be scalable to absorb other fulfillment actions over time.

The agent needs to read and write data from VTEX's Logistics APIs, follow the platform's agentic architecture standard (AI Workspace / Dark Kitchen), and be viable for Q2C2 without premature over-engineering.

The central decision is how to structure the repositories and the agents so the system is scalable, without creating unnecessary complexity at the start.

02Goal of This Cycle (Q2C2)
Cycle Goal

Set up the agent's backend. Have the backend prepared so that work on top of the agent can begin afterward — for example, already including logistics coverage analysis actions inside the Delivery Options feature we already have shipped.

This cycle is infrastructure-focused: the backend must be hosted, deployed, and observable following the platform standard, ready to receive agent tasks. Implementation of the analysis actions themselves comes in subsequent cycles.

03What the Agent Covers

The agent analyzes logistics configuration and real delivery behavior, explains risks and opportunities, and translates predefined diagnostics into editable action plans that are executed only after merchant approval.

INPUT — DATA READ
Fulfillment signals
  • Shipping policies (SLAs, costs, working hours)
  • Delivery Promise and shipping simulations
  • Aggregated order outcomes
  • Docks
  • Warehouses
→
REASONING
Understands routes
  • Derives delivery routes
  • Detects problems and gaps
  • Maps coverage & constraints
→
OUTPUT
Action plans
  • Delivery Option suggestions
  • Coverage and routing fixes
  • Individual or bulk approval
04Primary Objective

Recommend action plans based on predefined fulfillment diagnoses and execute them once approved by the Ecommerce Manager or Logistics Manager.

Concretely, the agent reads the signals in section 03, identifies risks and opportunities, explains the root cause and expected impact, and proposes editable Delivery Option, coverage, and routing actions for individual, partial, or bulk approval.

05Decision
Decision

Multi-agent architecture with an Orchestrator + specialized Sub-agents, two separate repositories (fulfillment-config-agent as a monorepo and fulfillment-mcp-server as a shared platform service), using the Strands framework.

06Options Considered
Option A — Single super-agentRejected

One agent with access to every domain (SLAs, docks, warehouses, DOs, inventory...).

Pros
  • Simple to start
  • Single deploy
  • Unified context
Cons
  • Context window grows with each new domain
  • Coupled deploy across domains
  • Reasoning quality drops as scope widens
  • Does not scale to other teams
Option B — Orchestrator + specialized Sub-agents (Strands)Chosen

An Orchestrator centralizes intent and delegates to domain-specialized sub-agents. Each sub-agent has a focused system prompt.

Pros
  • Lean system prompt per sub-agent
  • New domain = new sub-agent without touching the orchestrator
  • Independent deploy per component
  • Strands natively supports orchestration and chained tool calling
  • MCP Server reusable by other teams
Cons
  • More initial complexity vs. super-agent
  • Added latency per delegation hop
  • Sub-agents have no automatic template scaffolding
Option C — Multi-repo (one repo per agent from the start)Rejected

Each sub-agent in its own repository starting in Q2C2.

Pros
  • Granular ownership per repo
  • Fully independent deploy
Cons
  • Premature coordination overhead
  • Cross-dependencies hard to manage early
  • Multi-repo PRs for simple schema changes

09UI Strategy

The backend agent is decoupled from any specific UI. The frontend is out of scope for this cycle and connects to the orchestrator via API. The UI can take two forms:

UI OptionPlatform StandardNotes
Existing systems VTEX Raccoon or legacy Admin VTEX IO apps Some existing logistics surfaces already follow the Raccoon standard; others are more legacy apps on Admin VTEX IO. The agent can plug into these where it makes sense.
New agentic UIs Admin Shell / Raccoon New agentic experiences built for the agent, scoped to a future frontend spec.
10Consequences
✅Adding new domains (inventory, delivery windows) does not require refactoring the orchestrator — just a new sub-agent inside the monorepo with its own system prompt.
✅The fulfillment-mcp-server can be consumed by agents from other teams without coupling to fulfillment-config-agent.
✅Each sub-agent has a lean, domain-focused system prompt, preserving reasoning quality as scope grows.
✅The backend is decoupled from the UI, so it can serve both existing systems (Raccoon / Admin VTEX IO) and new agentic UIs without rework.
⚠️The Dark Kitchen template is run twice. Sub-agents inside the monorepo are created manually — no automatic scaffolding per sub-agent.
⚠️The fulfillment-mcp-server needs clear ownership — who maintains it, who approves breaking changes, how other teams contribute.
